# 模块实施与 SDD-TDD 验收计划

## 1. 文档目标与适用范围

本文件统一记录本项目的模块实施与验收方法，并提供已冻结里程碑的长期追溯入口。

本文件承担两项职责：

1. 记录 M1、M2、M3 已完成并上传的基线、冻结契约和对应 Git 提交证据。
2. 规定 M4 及后续模块统一采用的 SDD、TDD、独立复核、冻结和上传流程。

本文件不替代具体模块的 SDD。产品目标以 `docs/PRODUCT_REQUIREMENTS.md` 为准；每个里程碑的字段、接口、Schema、状态和业务规则以对应 `docs/M*_*.md` 为准；参与项目的 Agent 角色和授权边界以 `AGENTS.md` 为准。

本计划不记录当前测试通过数、临时未提交文件或短期进度。此类状态可能随工作区变化，必须在每次任务开始时通过 Git、实际代码和重新运行的测试确认。

## 2. 核心术语

- **Milestone（M）**：可以独立规划、实施、验收、冻结和上传的项目里程碑。
- **Module**：里程碑内具有明确所有者、输入、输出和物理文件边界的实现单元。本项目当前每次只实施一个用户批准的模块。
- **SDD**：Specification-Driven Development。实施前先冻结目标、公共契约、失败行为、排除范围和验收标准。
- **TDD**：Test-Driven Development。先通过公共语义契约形成有效红灯，再完成满足契约的最小实现并保持回归绿色。
- **冻结**：规格、公共契约、实现和契约测试经过独立复核，并由明确授权的 Git 提交固定。
- **上传冻结**：冻结提交已经推送到项目远程仓库，并重新确认本地与远程提交一致。
- **真实证据**：直接来自当前工作区代码、所有未跟踪文件、Git 差异、实际测试或真实基础设施的可复查结果。

冻结提交提供历史基线，但不能代替对当前工作区的重新检查。聊天摘要、实施报告和历史测试数字都不能单独证明当前状态。

## 6. M1/M2 对后续模块的继承约束

M3 及后续所有模块必须继承以下基线：

1. 后端继续在 Conda `web` 环境运行，前端继续使用现有 pnpm 锁文件和工具链。
2. 依赖方向保持从基础设施指向业务核心；domain 不得依赖 FastAPI、Agently、SQLite 或前端。
3. Agently 只能进入对应模型基础设施所有者，不得进入 domain、普通 DTO、文件处理或 Repository。
4. 题底和核心事实是服务端秘密，游戏结束前不得进入公开 DTO、前端状态、普通日志或错误信息。
5. M2 领域对象必须通过已冻结公共构造器和状态转换使用，不得绕过不变量重建或修改冻结字段。
6. 已冻结测试不得删除、弱化、改写或改成适应新实现。
7. 后续模块只能新增或修改其已批准 SDD 明确拥有的文件；修改冻结文件必须逐项说明兼容理由并事先取得批准。
8. 开始新模块前必须运行一次全量冻结基线，确认现有测试、静态检查和必要构建绿色。
9. fake/stub 只能验证调用契约和确定性分支，不能代替计划要求的真实 SQLite、真实模型或其他真实环境证据。
10. 不得通过默认结果、隐藏重试、自动修复、fallback 或模拟成功掩盖真实失败。

## 8. 角色与授权分工

### 8.1 用户

用户负责明确或批准：

- 当前处理的唯一模块。
- 模块范围和 SDD。
- 是否开始实施。
- 对冻结契约的任何修改。
- `git add`、`git commit` 和 `git push` 权限。

### 8.2 规划与复核

规划与复核职责包括：

- 根据真实仓库编写模块 SDD 和实施提示词。
- 在实施前识别冻结契约、文件所有者和排除范围。
- 实施后独立检查实际代码、全部未跟踪文件、Git 差异和测试。
- 发现歧义、范围越界、测试弱化或证据缺失时停止并报告。

规划批准、审查请求和历史授权都不构成编码或 Git 写操作授权。

### 8.3 实施

实施职责包括：

- 只实施当前获批模块。
- 依据批准 SDD 先建立契约测试，再编写最小实现。
- 保留冻结测试并运行适当回归。
- 如实报告实际文件、红灯、绿灯、失败和限制。
- 完成当前模块后停止，不提前进入后续模块。

## 9. 统一模块生命周期

所有新模块依次经过：

```text
冻结基线确认
  -> 模块范围确认
  -> SDD 编写
  -> SDD 复核与批准
  -> 实施提示词批准
  -> TDD Red
  -> 最小实现 Green
  -> 必要重构
  -> 实施交付
  -> 独立复核
  -> 冻结提交
  -> 推送确认
  -> 下一模块
```

任何门禁未满足时不得进入下一步。当前模块冻结并上传只表示允许规划下一模块，不自动授权下一模块实施。

## 10. 模块进入门禁

开始新模块前必须确认：

- 上一个模块冻结提交已经推送。
- 本地分支与预期远程分支关系已经重新检查。
- 工作区已有修改和全部未跟踪文件已经识别并归属。
- 上一个冻结基线的全量测试实际绿色。
- 当前模块拥有明确目标、所有者、输入、输出和排除范围。
- 当前模块不依赖未规划的后续实现。
- 所需框架和基础设施能够通过当前安装版本或真实环境核对。

如果前一基线失败或工作区证据无法区分，不得通过修改冻结测试进入新模块。

## 11. SDD 编写与审批

### 11.1 SDD 必备内容

每个模块 SDD 至少定义：

1. 阶段目标。
2. 所有者与依赖方向。
3. 允许新增或修改的物理文件。
4. 公共类型、方法和构造签名。
5. 输入和严格运行时规则。
6. 返回值、状态变化和不变量。
7. 失败契约。
8. 数据、事务或生命周期语义。
9. 安全与保密边界。
10. TDD 契约测试要求。
11. 明确排除范围。
12. 实施与验证命令。
13. 验收标准。
14. 冻结范围。

### 11.2 SDD 审批门禁

只有满足以下条件才可批准实施：

- 不存在会改变产品行为、公开接口、同步/异步属性、数据兼容性、成本或安全边界的未决歧义。
- 不与已冻结 SDD 和测试冲突。
- 输入、输出、状态与失败行为可以形成语义测试。
- 物理文件和模块所有者明确。
- 没有无当前消费者的接口、状态、数据表或抽象层。
- 自动化测试、真实环境证据和人工验收边界明确。
- 实施提示词能够逐项映射 SDD，而不需要实施者自行补充产品决策。

SDD 未获批准时只允许继续规划和修订文档，不得编写实现代码。

## 12. TDD 实施流程

### 12.1 Red

- 先为当前模块编写公共语义契约测试。
- 实际运行目标测试并保存退出状态和失败原因。
- 红灯必须由目标行为缺失导致。
- 环境损坏、命令错误、错误测试路径或破坏冻结模块不能冒充有效红灯。
- 对全新模块，因目标公共模块尚不存在造成的初始导入失败可以作为第一轮红灯；实现后仍必须由具体测试覆盖每项冻结语义。

### 12.2 Green

- 只实现满足当前 SDD 和测试的最小生产代码。
- 不得为了变绿删除、放宽或改写契约测试。
- 不得增加默认成功、模拟结果、隐藏 fallback、测试专用分支或无当前消费者的扩展。
- 模型或外部数据失败时不得写入成功状态或产生副作用。

### 12.3 Refactor

- 只在当前模块和冻结回归绿色后进行。
- 只整理当前模块实现，不改变公共语义。
- 不顺手重构冻结模块或无关代码。
- 重构后重新运行当前模块测试、冻结回归和适当全量检查。

## 13. 测试分层与证据真实性

按模块性质选择证据：

- **领域契约测试**：验证确定性业务语义和不变量。
- **Port 契约测试**：验证方法、参数、返回类型、同步属性和失败边界。
- **适配器测试**：使用真实 SQLite、文件系统或对应基础设施。
- **API 契约测试**：验证真实路由、DTO、状态码和题底保护。
- **前端测试**：验证公开交互、状态展示、错误保留和重复提交限制。
- **模型结构测试**：验证 Prompt 输入边界、结构化输出和宿主校验。
- **模型语义评测**：使用真实模型验证自然语言判断、注入防护和失败限制。

fake/stub 只能证明调用契约和确定性分支，不能证明 SQLite 事务、真实供应商调用或模型语义质量。人工验收应在自动化成本过高或结果天然具有语义性时使用，但必须记录环境、步骤、观察结果和限制。

## 14. 实施交付报告

实施完成后必须报告：

- 实际新增和修改文件。
- 实施前冻结基线结果。
- TDD 红灯命令、退出状态和真实原因。
- 当前模块测试结果。
- 冻结模块回归和适当全量检查结果。
- Git 状态、普通 diff、暂存 diff 和全部未跟踪文件。
- 密钥、题底和敏感配置扫描结果。
- 是否修改既有冻结文件及兼容理由。
- SDD 逐项符合情况。
- 尚未验证的限制和不能由 fake 证明的内容。
- 未执行的暂存、提交、推送或外部写入操作。

交付报告是复核入口，不是复核结论。报告中的命令和结果必须由独立复核重新检查。

## 15. 独立复核门禁

复核必须直接检查：

- 当前工作区真实源码和测试。
- 所有未跟踪文件的完整内容。
- `git status`、工作区 diff 和已有暂存 diff。
- 测试是否覆盖 SDD 公共语义，是否为了实现而弱化。
- 实际重新运行的当前模块测试和冻结回归。
- 真实基础设施、模型或人工证据是否满足计划。
- 密钥、题底、Prompt 和敏感数据是否泄露。
- 对冻结文件的每一项修改及兼容性依据。
- 框架使用是否符合当前安装版本真实源码和公开 API。

出现以下任一情况必须停止并报告：

- SDD 存在影响实现的歧义。
- 实现与冻结契约冲突。
- 实施越过当前模块。
- 测试被删除、放宽或改写以适应实现。
- fake/stub 替代了要求的真实证据。
- 框架接口只凭记忆猜测。
- 当前真实证据无法支持交付声明。

审查或状态报告不授权修改文件。除非用户明确要求修复，否则复核只报告问题、影响和建议。

## 16. Agently 专项门禁

涉及模型请求、Prompt、结构化输出、模型重试或其他 Agently 能力时，除通用门禁外还必须：

- 核对 Conda `web` 环境中当前实际安装版本。
- 读取该版本真实源码、公开 API 或项目示例。
- 模型请求和结构化输出使用 Agently 原生 ModelRequest 能力。
- TriggerFlow 只在 SDD 明确需要分支、事件、等待恢复、并发或可观察工作流生命周期时使用。
- ExecutionResource 或运行时扩展只进入其批准所有者。
- 禁止自建替代模型请求封装、隐藏 JSON 修复、隐藏重试循环或工作流框架。
- 模型输出在宿主校验前视为不可信，不得直接决定状态、权限或持久化。
- Prompt 或模型参数变化后执行最小真实模型语义评测。
- 记录使用的模型、环境、耗时、用量、观察结果和限制，但不记录密钥、完整敏感 Prompt、完整题底或隐藏推理。

Agently 原生能力缺失、接口不明确或与冻结 SDD 冲突时必须停止并报告，不得通过私有包装器或业务补丁绕过。

## 17. Git 冻结与上传门禁

### 17.1 冻结前检查

至少执行：

```powershell
git status --short --branch --untracked-files=all
git diff
git diff --check
git diff --cached
git ls-files --others --exclude-standard
```

同时必须：

- 单独读取普通 diff 不包含的未跟踪文件。
- 运行当前模块测试、冻结模块回归和适当全量检查。
- 运行静态检查、类型检查或构建门禁。
- 对所有版本控制候选文件执行密钥扫描。
- 检查是否提交数据库、运行时数据、缓存或生成产物。

### 17.2 暂存和提交

- 只有用户明确授权后才能执行 `git add` 和 `git commit`。
- 必须使用显式文件路径暂存当前获批范围。
- 提交前通过 `git diff --cached --name-only` 和完整暂存 diff 确认文件集合及内容。
- 不得顺带暂存用户或其他工具的无关修改。
- 提交后核对提交哈希、实际提交文件、暂存区和最终工作区状态。

### 17.3 上传确认

- `git push` 需要明确授权，或者由用户自行执行。
- 推送后通过 Git 重新确认本地分支和远程目标提交一致。
- 上传完成前不得实施下一模块。

## 18. 冻结契约变更流程

后续发现冻结契约确需改变时：

1. 停止当前模块实施。
2. 列出受影响的 SDD、公共契约、测试、数据和调用方。
3. 说明兼容性、安全性和迁移影响。
4. 提出完成当前目标所需的最小变更方案。
5. 取得用户明确批准。
6. 单独修订原规格和契约测试。
7. 重新运行受影响模块及全部冻结回归。
8. 独立复核并重新冻结。

不得通过兼容包装器、私有绕行、放宽旧测试或直接修改历史报告掩盖冻结冲突。

## 19. 模块完成定义

模块只有同时满足以下条件才算完成：

- SDD 已获批准。
- 实施范围与 SDD 一致。
- 有效 TDD 红灯和最终绿灯证据存在。
- 公共契约、失败路径和必要真实环境证据通过。
- 已冻结模块测试保持绿色且未被弱化。
- 独立复核没有阻断问题。
- Git 差异、未跟踪文件、空白和密钥检查完成。
- 获准的冻结提交已经创建。
- 冻结提交已经推送并重新确认。
- 没有提前实现下一模块。

完成当前模块后停止，等待用户批准下一阶段。

## 21. M5-M9 长期路线规划

### 21.1 路线定位与阶段依赖

M5 至 M9 用于在 M1-M4 基础上完成单人海龟汤 MVP。长期依赖顺序固定为：

```text
M1 架构与项目结构
  -> M2 领域核心
  -> M3 Repository 与 SQLite
  -> M4 正式题库
  -> M5 模型语义判定
  -> M6 应用用例编排
  -> M7 HTTP API
  -> M8 前端游戏闭环
  -> M9 MVP 集成验收
```

依赖箭头表示后续阶段可以使用前一阶段的冻结公共契约，不表示可以修改前一阶段所有者。任一阶段只有在前一阶段冻结并上传后才能开始规划实施；阶段主题写入本路线图不构成 SDD、编码或 Git 授权。

M4 为 M5 提供经过来源和内容审查的代表性正式题目，使真实模型评测不依赖临时、来源不明或为测试过拟合的题目。M5 为 M6 提供纯语义判断 Port；M6 负责确定性业务编排；M7 和 M8 分别负责传输及展示；M9 只验证组合后的真实闭环。

### 21.2 M5 模型语义判定

#### 阶段目标

M5 只负责两个契约独立的模型请求家族：

1. 根据题面、题底、核心事实、当前问题和必要的有界历史，将玩家问题判定为 M2 `Verdict`。
2. 根据题面、题底、核心事实、当前最终猜测和必要的有界历史，判断是否命中核心真相并返回布尔结果。

#### 所有者边界

- domain/application 一侧拥有模型语义 Port、输入边界和宿主程序消费契约。
- 模型基础设施所有者使用 Agently 实现 Port，拥有模型设置映射、Prompt、ModelRequest 和结构化输出适配。
- 模型拥有自然语言理解、相关性和语义判断。
- 宿主程序拥有类型、枚举、必填字段、状态、权限、持久化、可信标识和副作用。
- M5 不读取或写入 Repository，不转换游戏状态，不创建回合记录，不生成 ID 或时间。

#### Agently 能力选择

- 问题判定和最终猜测判定使用两个独立的 Agently ModelRequest 请求家族，不合并为一个通过自由文本路由的通用请求。
- 每个请求使用原生 `input`、`info`、`instruct` 和 `output` 槽位表达运行时输入、权威题目信息、判定规则和机器可消费输出。
- 调用链采用异步最终结果消费；当前没有渐进式结果消费者，不打开并丢弃 streaming。
- 结构化输出使用 Agently 原生能力和宿主确定性校验，不自建 JSON 修复、Prompt 模板系统或隐藏重试循环。
- 当前产品没有需要框架可见的分支、并发、暂停恢复、审批或持久工作流生命周期，因此 M5 不使用 TriggerFlow。
- 实施前必须重新核对 Conda `web` 中实际安装的 Agently 版本、真实源码、公开 API 和最小代表性调用，不依赖 M1 记录或本路线图猜测接口。

#### 核心交付

- 两个异步模型语义 Port 及其冻结输入、输出和失败边界。
- 两个独立、可版本控制的 Prompt/输出契约。
- 环境变量到 Agently provider 设置的映射及缺失配置 fail-fast 行为。
- Agently ModelRequest 适配器和宿主程序结构化结果校验。
- 框架契约、Prompt 输入边界、非法输出和模型失败的确定性测试。
- 使用 M4 代表性题目的最小真实模型语义评测及限制报告。

#### 验收证据

- 问题判定只接受 `YES`、`NO`、`IRRELEVANT`，并可靠映射为 M2 `Verdict`。
- 最终猜测判定只接受严格布尔结果。
- 玩家输入被作为待判定数据，不覆盖系统规则或权威题底。
- 模型失败、空结果、非法结构或非法枚举明确失败，不产生默认答案。
- 确定性测试证明框架调用与宿主校验；fake/stub 不被用来证明模型语义质量。
- 真实模型评测至少覆盖明确的是、明确的不是、无关、含糊口语、套取题底、正确改写猜测和只命中部分事实的猜测。
- 真实评测记录实际模型、调用次数、耗时、用量、观察结果和限制；无法获取的遥测标记为不可用，不推测或伪造。
- Agently 使用具有当前安装版本源码/API 证据，并通过原生能力合规和反模式检查。

#### 明确排除

- 游戏状态转换、回合保存和应用用例。
- FastAPI、HTTP DTO、前端展示或中文回答映射。
- 自动生成、改写或在线抓取题目。
- 评分、置信度、长篇解释、隐藏推理、长期记忆、向量检索、多 Agent 或 TriggerFlow。

### 21.3 M6 应用用例编排

#### 阶段目标

M6 组合 M2 领域、M3 Repository、M4 正式题目和 M5 模型语义 Port，建立开始游戏、提问、提交最终猜测、放弃游戏和读取游戏的应用用例。

#### 所有者边界

- application 拥有用例顺序、限制策略、可信 ID/时间供给、模型上下文投影和副作用边界。
- M2 domain 仍独占状态转换和领域不变量。
- M3 Repository 独占持久化表示和事务实现。
- M5 模型 Port 独占语义请求，不拥有状态或写入。
- M6 不依赖 FastAPI、Pydantic、React 或具体模型 provider。

#### 核心交付

- 开始游戏、记录问题、提交猜测、放弃游戏和读取游戏的应用契约。
- 可信 ID 与带时区时间的宿主供给边界。
- 玩家输入长度、单局回合数和模型历史窗口的确定性限制。
- M3 同步 Repository 与异步模型调用之间的明确调度所有者。
- 领域对象到应用结果的安全投影，不在进行中结果暴露题底或核心事实。
- 模型和数据库失败时不伪造成功、不写入成功回合的原子失败行为。

#### 验收证据

- 开局只选择启用题目并保存空的 `PLAYING` 会话。
- 提问流程遵循“读取与校验 -> 模型判定 -> 构造领域记录 -> 保存 -> 返回”。
- 猜测流程在未破解时保持 `PLAYING`，破解时通过 M2 转换为 `SOLVED`。
- 放弃通过 M2 转换为 `ABANDONED`，终局后所有写操作被拒绝。
- 输入、回合和历史限制在调用模型前执行。
- 模型失败不新增记录，Repository 失败不返回成功。
- 确定性用例测试可以使用 Port fake 验证编排，但 M5 真实语义证据仍需独立保留。

#### 明确排除

- HTTP 路由、状态码和 Pydantic DTO。
- 前端状态与用户交互。
- Prompt、Agently 设置、SQL 或题库内容编辑。
- 登录、多用户所有权、排行、推荐或后台任务。

### 21.4 M7 HTTP API

#### 阶段目标

M7 将 M6 用例通过 FastAPI 暴露为受控 JSON API，使前端能够开始游戏、读取游戏、提问、猜测和放弃，同时严格保护题底和核心事实。

#### 所有者边界

- transport 拥有 HTTP 路由、Pydantic DTO、入站校验、状态码、错误投影和公开响应。
- application 继续拥有用例顺序与业务限制。
- domain 继续拥有游戏规则。
- 基础设施组合入口负责启动时数据库初始化和模型设置装配，但路由不得直接调用 SQL 或 Agently。

#### 核心交付

- 开始游戏、读取游戏、提问、最终猜测和放弃的 HTTP 契约。
- `PLAYING` 与终局状态的独立公开响应投影。
- 应用、领域、模型和持久化失败到 HTTP 错误的确定性映射。
- API 启动配置、SQLite/模型依赖装配和缺失配置 fail-fast 行为。
- 模型请求频率、同会话重复并发提交和传输层输入边界。

#### 验收证据

- 公开路由只调用 M6 用例，不复制领域或 SQL 逻辑。
- `PLAYING` 响应不包含 `solution` 或 `key_facts`。
- `SOLVED`、`ABANDONED` 仅按 M2 许可公开 `solution`；`key_facts` 始终不进入公开 DTO。
- DTO 拒绝非法类型、空白输入、超长输入和未知字段。
- 非法状态、目标不存在、模型失败和数据库失败返回稳定、可识别且不泄密的响应。
- API 契约测试可用 fake 模型 Port 验证确定性投影，但不能替代 M5 真实模型评测。

#### 明确排除

- React 页面、浏览器状态和视觉设计。
- 用户登录、多人授权、公开部署、WebSocket 或流式模型输出。
- 模型 Prompt、SQLite Schema 和正式题库内容。

### 21.5 M8 前端游戏闭环

#### 阶段目标

M8 使用现有 React、TypeScript 和 Vite 基线实现移动端与桌面端均可完成的一局单人海龟汤游戏。

#### 所有者边界

- frontend 拥有浏览器状态、API client、公开 DTO 类型、加载/错误状态、交互和响应式布局。
- 后端 M7 API 是前端唯一业务数据来源。
- 前端不得拥有题底公开规则、语义判定、状态转换、模型调用或数据库访问。

#### 核心交付

- 开始游戏和恢复当前游戏状态。
- 始终清晰展示题目标题与题面。
- 问题历史及“是/不是/无关”的用户可见映射。
- 明确分离“提问”和“提交最终猜测”。
- 加载期间防重复提交，失败后保留玩家输入并允许重试。
- 放弃确认和终局题底/记录展示。
- 移动端可完成全部流程的响应式交互。

#### 验收证据

- API client 与公开 DTO 投影测试。
- 开局、提问、猜测、放弃、终局和重新读取状态的组件/交互测试。
- 请求失败保留输入、重复提交保护和放弃确认测试。
- 前端类型和浏览器状态中不存在 `key_facts`，进行中状态不存在 `solution`。
- 前端 test、lint 和生产构建绿色。
- 移动端视口下完成整局的浏览器或人工验收证据。

#### 明确排除

- 模型与题库业务逻辑、客户端答案判断或题底解密。
- 登录、多人、排行、推荐、语音、图片和复杂动画。
- 前端持久保存密钥、完整敏感 Prompt 或服务端秘密。

### 21.6 M9 MVP 集成验收

#### 阶段目标

M9 不新增产品功能，只验证 M1-M8 组合后是否形成真实、安全、可重复的 MVP 完整闭环。

端到端路径为：

```text
正式题库
  -> SQLite
  -> 开始游戏
  -> 提问
  -> Agently 模型判定
  -> 保存记录
  -> 最终猜测或放弃
  -> 终局
  -> 公开题底
  -> 前端完整展示
```

#### 所有者边界

- M9 拥有跨模块验收矩阵、端到端测试入口、真实环境证据和最终限制报告。
- M9 不成为新的业务规则、兼容包装器或通用修复所有者。
- 发现缺陷时必须定位到 M1-M8 的真实所有者，按冻结契约变更流程取得批准后修复并重新验收。

#### 核心交付

- 一局完整成功路径和放弃路径的端到端证据。
- 真实 SQLite 文件、真实 API、真实前端和获准真实模型的组合验证。
- 模型、数据库、输入、频率、并发和终局失败路径验证。
- 题底、核心事实、密钥和 Prompt 泄露检查。
- 移动端完整流程验收。
- 全量测试、静态检查、构建、密钥扫描、真实模型用量和限制汇总。

#### 验收证据

- 玩家能够从前端开始并完成一整局。
- 问答只产生受控三分类，最终猜测产生严格布尔判断。
- 模型失败不保存成功记录，数据库失败不返回成功。
- 终局后拒绝继续提问、猜测或再次终局转换。
- 游戏结束前 API、前端、日志和错误不泄露题底；`key_facts` 始终不公开。
- Prompt 注入和套取题底案例不会改变输出契约或泄露秘密。
- 输入长度、最大回合数、模型超时、请求频率和同会话并发限制实际生效。
- 真实模型评测与确定性测试分别报告，不以 fake、关键词或单次幸运输出证明语义质量。
- 所有冻结模块回归保持绿色，版本控制候选文件无密钥或运行时数据。

#### 明确排除

- 新增业务功能或顺手重构冻结模块。
- 公网部署、生产运维、备份扩容和多实例并发方案。
- 登录、多人、排行、推荐、自动生成题目、语音、图片、长期记忆或多 Agent。
- 为通过验收而弱化历史测试、修改冻结契约或隐藏真实失败。

### 21.8 路线图变更边界

- 本路线图只冻结阶段顺序、所有者方向和 MVP 能力归属，不提前冻结 M5-M9 的文件名、公共签名、DTO 字段、限制数值或物理目录。
- 每个阶段开始时必须根据真实工作区和已上传基线单独编写完整 SDD。
- 如果后续证据表明阶段需要拆分、合并或调整依赖，必须在开始相关实施前修订本计划并取得用户批准。
- M9 完成前不规划超出 MVP 的部署、账号、多人、排行、推荐或内容生成能力；这些属于独立的后续路线，不得夹带进入 M5-M9。
